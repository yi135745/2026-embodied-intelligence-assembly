# 工作流、验证与实机边界

## 先识别请求模式

| 用户意图 | 允许动作 |
| --- | --- |
| 解释、回顾、讨论、先回答 | 只读代码、历史、日志和报告；不给正式文件打补丁 |
| 诊断 | 找到原因、复现或提出试验；除非同时要求修复，否则不改业务实现 |
| 修改、批准开工 | 在已讨论边界内实现，保留现有接口和现场数据，做相称验证 |
| 测试相机/盒子/API | 只执行所点名设备或服务；说明占用、成本和输出 |
| 真机运动/抓放/Tool IO | 必须是明确的本轮请求；代码修改授权不自动包含执行授权 |

用户改变优先级时停止旧方向，不要因为已经写了方案就继续。

## 当前任务二正式现场链路

依次运行，不并行：

```powershell
python tools/setup/aubo_pose_recorder.py
python tools/task2/workflow/task2_tuner.py
python tools/task2/workflow/task2_tuner.py --scene tray
python tools/task2/workflow/task2_tray_auto_calibrate.py
python tools/task2/workflow/task2_closed_loop_offset_calibrate.py
python tools/task2/workflow/task2_calibration_audit.py
```

语义：

1. 记录四个正式拍照位；位姿 JSON 是唯一来源。
2. 分别调方块九色和托盘六色，不用放宽完整性代替调参。
3. 托盘区走一个 3×3 相机运动网格，每帧最多观察六个托盘中心，拟合方块/托盘唯一公共矩阵。
4. 先依次人工建立方块区、托盘区两个绝对XY锚点；两次都完成后，按同一工具中的采样方案自动做平移、旋转、跨区托盘落点观测和独立验证，生成双区 XY 偏移及同文件动作补偿模型。
5. 审计矩阵质量、公共位姿条件和偏移指纹。

新设备不要求历史版存在，但要求正式矩阵有可追溯质量、完整报告和对应偏移。历史备份用于恢复，不是新机部署前置。

闭环偏移的 `quick` 与 `robust` 方案只能改变自动采样数量，不能改变正式矩阵、偏移文件或误差阈值。托盘样本必须在同一冻结偏移下从物块区独立出发并取回；托盘到托盘的相对搬运会使托盘偏移在抓取和放置中相消，不能作为绝对托盘偏移样本。自动落点残差只拟合动作补偿，不回写人工建立的坐标偏移；少样本自动降阶为常量+旋转或常量模型，报告必须明确模式与数量，不能伪造空间重复性结论。

`--compensation-model constant` 是同一闭环工具和正式数据接口下的对照模式，不是第二份状态源。它只能把落点残差的二维中位数写入 `constant_bias_mm`，空间矩阵和旋转偏心必须归零，并使用独立验证抓放验收；`adaptive` 才允许拟合空间与旋转项。

偏移工具必须在方块人工锚定后写检查点，并在双锚定后先生成可验证候选再进入自动采样。`--manual-only` 是同一正式偏移接口的保底模式：只用 SDK 读取的两个 TCP 中心建立固定 XY 偏移，所有动作补偿项置零。标定专用 `--board-guard fallback` 可在白板边界失败时降级为全画面 HSV 单目标审计，降级原因必须写入报告，且不得放宽正式任务抓放门禁。

普通闭环运行在双人工锚点落盘后也必须提供一次现场中断选择：可继续自动模型、以同一人工零补偿候选进入启用事务，或仅保留候选退出。中断不得丢失人工结果，也不得绕过明确启用确认。

人工锚定与自动采样开始前的静态复拍可用像素位移门禁阻止场景被误碰；抓放后的自动取回可能因柔性吸盘释放产生真实落点偏移，该偏移必须换算为毫米并记录为重复性证据，不能复用“场景未变化”门禁在检测前中止，也不能静默当作人工锚点误差。

正式任务的白板区域门禁由 `TASK2_BLOCK_BOARD_GUARD_MODE` 控制。`fallback` 只在白板边界定位失败时退回全图形状/颜色识别，不能跳过任务卡动作校验、所需颜色完整性、轮廓尺寸或坐标版本门禁；必须输出明确警告，禁止静默降级。

## 标定启用事务

候选矩阵按以下边界处理：

```text
采集原图/实际TCP
  -> 离线拟合候选 XML + 完整报告
  -> 点数/矩阵结构校验
  -> world RMS / pixel RMS 质量门禁
  -> 人工核对标注图并输入 yes
  -> 备份旧正式 XML
  -> 原子写正式 XML、绑定摘要、持久报告
  -> 旧 XY 偏移自然失效
  -> 重新运行闭环偏移
```

不得通过删除 binding、复制旧偏移指纹、提高阈值或把 UNKNOWN 当 PASS 来解除阻塞。若纯平移残差大，先查错检、点位、单位、矩阵与偏移是否混版；该残差不能解释为旋转偏心。

## 调试入口分类

- `tools/task2/workflow/`：会修改现场调参或正式标定，部分会运动。
- `tools/task2/diagnostics/`：用于视觉、托盘和高度对照；是否运动以脚本说明为准。
- `tools/setup/`：读取/写入机器人点位或 Tool IO，通常需要实机。
- `test/`：只保留可自动发现、无硬件副作用的离线回归；设备检查需要时在 `tools/diagnostics/` 建立明确入口。

`TASK2_EXECUTE_ROBOT=False` 只约束任务二正式流程，不是所有工具的全局急停开关。

HSV 调参工具必须用当前候选参数调用正式 `ColorObjectDetector` 做同屏预览，不能只显示单色掩膜来冒充正式效果。同色多段 HSV 必须可分别编辑；人工确认应保存原图、正式标注结果、检测对象和当时参数，但运行时参数仍以唯一 `data/task2_tuning.json` 为准。

## 安全与权限边界

- 跨区域用 `move_to_safe()`；抓放用 `pick_and_place()`，不能互换语义。
- 放置释放采用开泄压阀与气泵短时重叠、停泵后保持泄压、低速竖直脱离、再关阀的顺序；抓取压缩与吸取不复用释放慢抬参数。改变重叠时间、泄压时间、慢抬距离或速度后必须重新做单块受控验收，闭环落点误差不能混入坐标偏移。
- `ROBOT_SAFE_Z`、抓取 Z、放置 Z、速度和 TCP 都是现场量；换机、换工位、换相机高度或工具后重新验收。
- 拍照位之间自动运动前加载并检查当前 `aubo_poses.json`；不要把历史 JSON 当当前设备事实。
- Tool IO 是末端 IO0/IO1 与 12V 配置；写 IO 前确认实际硬件，读取状态不等于授权启停。
- MVS、VisionMaster 和脚本可能互斥占用相机；失败时先释放占用，不通过重复启动制造更多状态。
- 外部视觉模型可能计费且依赖密钥；离线测试应使用 FakeLLM 或静态数据。
- 不在代码、Skill、README 或日志摘要中保存 AI 盒子、机器人或 API 密码。

## 验证层级

1. **静态/离线**：编译、unittest、纯拟合回放；证明接口和算法回归，不证明实物。
2. **静态图**：检查颜色、形状、中心和方向；证明当前图片可处理，不证明不同光照和边缘位置。
3. **设备单项**：相机、盒子、机器人读取、Tool IO 分开验收。
4. **受控运动**：低速、单块、单托盘、平移、旋转、叠放逐级验收。
5. **完整任务**：按任务卡执行并统计时间、残差和失败率。

Python 代码变更的最低离线回归：

```powershell
python -m compileall -q main.py task modules drivers contracts runtime tools test
python -m unittest discover -s test -q
```

测试数量会随工程增长，不在 Skill 中硬编码；以本次实际输出的 `Ran N tests` 和 `OK` 为准。

## 修改完成检查

- 是否无意新增第二数据源、第二矩阵或第二入口？
- 是否仍保持 mm/rad 与 SDK m/rad 的转换边界？
- 是否让正式运行依赖了可删除的 `output/`？
- 新矩阵是否会正确使旧偏移失效？
- 失败是否停止后续动作并留下原图/候选/日志？
- 是否把调试确认删掉后仍有确定的前置门禁和清晰训练路径？
- README 面向操作员、Skill 面向 AI 的内容是否各自更新？
- 最终说明是否区分离线通过和实机待验收？
