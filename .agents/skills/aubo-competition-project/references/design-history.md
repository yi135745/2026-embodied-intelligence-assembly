# 设计沿革与已验证教训

## 这套框架如何形成

本工程的结构来自多轮实机约束，而不是一次生成：先建立语音派发、MVS、Qwen、AUBO 和吸盘的分层接口；再在不同机器、工位和比赛现场反复处理安全运动、坐标单位、Tool IO、颜色、偏移和时间压力。理解这些约束是修改工程的一部分。

Git 中的重要参照：

- `final-demo` 标签及其前后提交记录了早期可演示链路。
- `bd66985`（`save final competition version`）是省赛完赛封存基线。比较“省赛原设计”和“国赛扩展”时，以它为主要代码参照，不凭记忆猜测。
- 当前工作树包含国赛适配和现场数据，可能尚未提交；不得为了得到干净 diff 而覆盖它。

## 省赛已经确立的设计

- 两段式语音：先唤醒，再派发任务；任务文件不重复唤醒。
- `main -> task -> modules -> SDK` 的分层。
- 所有路径锚定项目根，运行产物集中在 `output/`。
- 四个拍照位使用统一六维格式，跨区域经过安全 Z。
- MVS 只拍照，OpenCV 做物块/托盘检测，`Interpreter` 只读任务语义。
- 像素先经九点矩阵变为平面增量，再叠加分区原点和 XY 偏移。
- 方块和托盘拍照位刻意保持同 Z、同 RZ，因此共用一份矩阵；两区只分别校正 XY 偏移。
- 吸盘使用 AUBO 末端 Tool IO，电压、方向、输出模式和回读都需要显式处理。
- 现场数据必须随机器和工位重新标定，代码默认值不能替代验收。

## 国赛在原框架上的扩展

- 任务卡协议从固定 `block_color/tray_color` 扩展为 `source_color/target_type/target_color`，支持落盘与叠放。
- 方块从六色扩展为九色；托盘仍为六色。
- 增加纯计算 planning 层，先验证整份动作，再推演方向、高度和终态。
- 矩形方向通过公共矩阵转到机器人 XY，不直接使用图像角。
- 抓放支持高位旋转与按实测高度叠放。
- AI 盒子通过 `modules/voice.py` 适配，业务层接口保持不变。
- 视觉增加白板区域、近方形、边缘轮廓、HSV/Lab 联合分配，解决强补光和低饱和棕色问题。
- 根目录调试脚本先按 workflow/diagnostics/legacy 整理；架构收束后删除未使用的 legacy，只保留 workflow 与 diagnostics，进一步减少现场选错入口。
- 托盘九点利用一次 3×3 运动同时观察最多六个中心，缩短标定；闭环偏移先分别建立方块区、托盘区人工绝对锚点，再自动做可变数量的平移、旋转和跨区落点验证。

这些扩展应当复用原有设备接口和坐标模型，而不是平行建立“国赛专用第二套系统”。

## 已发生过的架构偏移

### 把公共矩阵拆成方块/托盘两套

这违背了原先“同 Z、同 RZ、只改 XY”的现场布置意图，导致两个质量门禁、两个指纹和偏移混版。正确方向是托盘多观测生成唯一公共矩阵，方块区用纯平移真机验收其可迁移性。

### 把 `output/` 报告当长期依赖

清理输出后质量变 UNKNOWN，闭环也失去 54 组观测。现在完整报告和质量摘要随正式矩阵固化到 `resources/`；`output/` 只保留证据副本。

### 模板来自正在使用的正式文件

误删或覆盖正式 XML 会同时失去模板。现在模板独立只读，候选由模板生成，正式文件只能通过版本工具启用。

### 用错误点降低整体矩阵质量

单次颜色错检可以让图像看似正常但对应关系错误，产生很大的 RMS 和平移残差。处理方式是检查标注、对应和原始样本，不是放宽质量门禁或把误差算作旋转偏心。

### 新矩阵继续沿用旧偏移

矩阵和偏移共同决定机器人 XY。新矩阵启用后旧偏移必须 STALE；自动改指纹只会掩盖混版。

### 用相对九点拟合残差代替托盘绝对锚点

托盘九点自动运动能拟合像素位移与机器人平面位移的比例、方向和透视，但其世界原点仍有未知平移。用同一批观测先估计托盘位置、再反算偏移，只会得到接近零的内部残差，不能得到相机到TCP的绝对平移。公共矩阵不变，方块区和托盘区仍必须分别进行一次人工XY粗对准；随后自动落点只能进行小范围结果修正。

### 调试入口和确认过多

比赛现场时间紧，常用工具应有固定默认场景、自动移动和可训练的一键入口。但减少人工确认不能删除质量门禁、正式覆盖确认、备份或异常停止。

## 如何判断一个新想法是否越过框架

先回答四个问题：

1. 它是在现有真源上增加观测或校验，还是增加了另一个真源？
2. 它改变模块职责，还是只改模块内部实现？
3. 它能用离线/静态/单项设备试验逐级证明，还是必须一次重写整条链路？
4. 失败后能否回到旧正式数据，并从日志明确知道失败位置？

若答案涉及第二真源、跨层职责、无法分级验证或不可回退，先作为架构方案与用户讨论，不直接编码。
